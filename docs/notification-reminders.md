# 下班打卡提醒

在“通知 → 设置 → 下班打卡提醒”中配置一条规则。功能默认关闭，保存设置后才生效。

## 配置

1. 在通知访问授权中选中签到应用，确认“通知历史”能收到它的通知。
2. 点击“来源应用”，在与通知筛选类似的面板中按应用名称或包名搜索，点击对应应用选中。列表来自通知历史，不枚举全部已安装应用；找不到时先完成通知访问授权并接收该应用通知，再刷新来源列表。无需手动填写包名。
3. 填写成功通知标题或正文实际包含的关键词，例如“下班打卡成功”。关键词按原文区分大小写，不使用正则；避免只写“成功”，以免把上班打卡等通知算作完成。
4. 设置接收起始时间和提醒时间，使用 `HH:mm` 格式。默认接收范围为当天 `17:00 ≤ 通知时间 < 20:00`，提醒时间为 `20:00`，不支持跨天。
5. 打开启用开关并保存，在手机弹窗中允许日历读写，确认状态显示“已安排系统日历”。也可先点击“授权日历读写”。开关和输入修改均须保存。

选中来源只更新编辑草稿，不会立即修改已保存的提醒；关闭选择面板不改变来源。旧配置中的包名仍兼容；若通知历史已清空，显示已保存的包名，不自动清除原规则。

生效日期按中国工作日安排：法定节假日不提醒，周末调休上班日会提醒。2026 年采用国务院办公厅公布的放假调休日期；尚未公布安排的年份暂按周一至周五预排，后续年度数据随应用更新补齐。此规则不识别个人请假或单位自定工作日。

提醒由系统日历发出：日程标题为“下班打卡提醒”，说明为“尚未收到下班打卡通知，请检查是否忘记打卡”。未收到通知不能证明没有打卡；原应用未发通知、通知订阅被关闭或系统延迟投递都可能造成提醒。声音受系统日历的通知、静音和勿扰设置影响。

## 权限

- 继续使用既有 `ohos.permission.SUBSCRIBE_NOTIFICATION` 和用户选定的通知来源。
- 声明 `ohos.permission.READ_CALENDAR` 和 `ohos.permission.WRITE_CALENDAR`，由用户在手机授权，不需要申请代理提醒开放能力。
- 在系统日历设置中允许日历应用发送通知，并开启“下班打卡提醒”日历的提醒。
- 不再声明 `ohos.permission.PUBLISH_AGENT_REMINDER`，也不为本功能申请后台常驻、定位、全部日历访问或网络权限；不修改本机签名配置。

保存时若用户拒绝日历权限，保留编辑草稿，不登记日程；系统登记失败则保留已保存配置并显示“提醒未就绪”及错误信息。处理权限后点击“刷新并重试”。配置已保存不代表系统日程已安排成功。

## 实现与数据

`NotificationReminderEngine` 和 `ChinaWorkdayCalendar` 使用同一份离线工作日表判断通知日期；`NotificationReminderService` 通过 `CalendarReminderGateway` 对接 Calendar Kit，在专用本地账号 `com.gyg.harmonyledger.attendance`（显示名称“下班打卡提醒”）中创建周一至周五重复日程，按法定节假日设置重复排除日期，并为周末调休上班日创建单日提醒，设置 `reminderTime: [0]`。不使用默认或云端日历，不访问其他账号的日程；只管理 identifier 为 `com.gyg.harmonyledger.attendance.reminder.v1` 及其 `.makeup.` 前缀下的日程。

2026 年工作日数据依据[国务院公报 2025 年第 32 号中国务院办公厅的通知（第 17 页）](https://www.gov.cn/gongbao/2025/issue_12406/material/gwygb202532.pdf)。官方新增或更正年度安排后，应用内置表和 `CHINA_WORKDAY_CALENDAR_VERSION` 需随版本更新；打开或刷新提醒设置时会按新表重建日历日程。年度版本存于 `notification_reminder.db` 的现有 JSON 状态中，不更改 SQLite 表结构。

收到匹配通知后更新日程的 `recurrenceRule.excludedDates` 跳过当天，排除时间与日程开始时间的时分秒完全一致，不直接使用打卡通知时间，并保留其他排除日期。重复通知不会反复更新，也不会生成第二条日程。请勿在日历应用中手动修改本功能生成的日程；删除日程后，应用恢复或点击刷新会重新创建。

`NotificationProbeExtension` 使用独立提醒队列，提醒失败不阻断通知归档和自动入账。优先使用通知自身的有效发布时间，没有时使用接收时间；只接受同一当地日期的通知，拒绝未来时间和窗口外通知。即使发布时间在窗口内，截止后才实际收到的通知也不算按时完成。

配置、日历日程标识、最近完成日期及错误状态单独保存在 `notification_reminder.db` 中，不保存通知标题或正文。事务和进程内队列协调页面、前台恢复与通知扩展的并发更新，不修改 `harmony_ledger.db` 或 `notification_archive.db`。新增可选 backend 字段识别执行方式，无须更改已有表结构。旧版数据保留配置和完成记录，先撤销已知旧代理提醒，再清空旧标识并安排日历日程；旧代理提醒编号不会用于删除日历日程。兼容代码仅调用旧计划的取消接口，不再发布代理提醒。当前完整 JSON 备份不包含这项提醒设置，重新安装后需重新配置。

保存、刷新和应用回到前台时核对日程；丢失则重建，中断产生的本功能多余日程会被清理，不触碰其他日程。停用时删除本功能创建的日程，保留空的专用日历账号。调整来源、关键词或接收起始时间后清除旧匹配结果，不回放历史通知。调整提醒时间时，仅保留仍处于新窗口内的当天匹配结果。

启用或恢复时如果当天提醒时间已过，从下一个生效日期开始安排，不补发过去的提醒。晚于截止时间才投递给本应用的成功通知可能来不及阻止已经发出的提醒。应用不能在通知订阅失效时推断是否打卡；后台可靠性须使用实际签名包在真机验证。

来源选择改为搜索列表后，在模拟器验证了打开来源列表、包名搜索、点击选中、选中标记和未保存返回后的配置保留；未保存测试选择。自动化覆盖应用名及包名搜索、选择仅更新草稿、取消加载、快速重开的请求隔离，以及读取失败后重试和旧来源保留。

真机需验证：拒绝和授予日历读写；专用日历和日程的创建及停用清理；工作日把提醒时间设为几分钟后，锁屏等待系统日历提醒；法定节假日不提醒；调休周末创建日程且收到成功通知后跳过当天；下一工作日仍提醒；修改设置；重启后的日程及日期排除恢复。不能用模拟日历 API 的测试代替这些验证。
